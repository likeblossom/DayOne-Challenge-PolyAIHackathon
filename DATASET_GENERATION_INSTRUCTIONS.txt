INSTRUCTIONS FOR A DATASET-GENERATION GPT
=========================================

GOAL
----
Build and run a CUDA-first generator for a large multilingual synthetic maternal-form
training dataset. Generate every image and label from scratch. The organizer dataset is
reserved strictly for final testing.

NON-NEGOTIABLE RULES
--------------------
1. DO NOT read, copy, transform, sample, trace, derive styles from, or train on anything in:
   - dayone-participants/
   - derived_image_label_dataset/
2. DO NOT use organizer CSV rows as seeds or distributions.
3. You MAY read form_structures/ because those files define the required output fields.
4. Generate the ground-truth record first. Render the image from that exact record.
5. Never accept an image-model transcription as ground truth.
6. Use only synthetic identities. Do not generate names, addresses, phone numbers, national
   identifiers, or any other direct patient identifiers.
7. Prefer CUDA for rendering models, handwriting synthesis, and augmentation. Print whether
   CUDA is active. Fall back to CPU only when an operation has no useful GPU implementation.
8. Make the run deterministic from a configurable random seed.
9. Do not commit the generated images to GitHub. Commit only generator code, configuration,
   documentation, and small previews.

FORM TYPES
----------
Generate each form type independently:

01. Pregnancy and Postpartum Monitoring
02. Identification and Medical History
03. Current Pregnancy
04. Course of Labor and Delivery
05. Early Postpartum Visit — Mother
06. Early Postnatal Visit — Newborn
07. Late Postpartum Visit — Mother
08. Late Postnatal Visit — Newborn

Use form_structures/*.schema.json for the field names and field types. Produce a distinct
layout for each form. The layouts must be newly created and must not be copied from the
organizer images.

DEFAULT SCALE
-------------
Make scale configurable. Use these defaults on the stronger computer:

- 1,000 full pages per form type
- 8,000 full pages total
- Save every individual field crop as well as the full page
- This should produce tens of thousands of labeled field crops

Allow a smoke-test option such as --per-form 3 before the full run.

LANGUAGES
---------
Balance the data across:

- English
- French
- Arabic
- Mixed-language pages

Include both Western digits and Arabic-Indic digits. Arabic must render right-to-left with
correct connected shaping. Include realistic French accents. Keep a canonical English value
in the labels and separately store the exact visible transcription.

Examples:

canonical_value: 43
rendered_text_en: "43 days"
rendered_text_fr: "43 jours"
rendered_text_ar: "٤٣ يومًا"

HANDWRITING DIVERSITY
---------------------
Use multiple licensed sources and methods:

- Many licensed handwriting fonts
- Text-conditioned handwriting synthesis models, if available
- Different writer embeddings/styles
- Blue and black ballpoint ink
- Different stroke widths, pressure, slant, spacing, size, and baseline drift
- Connected and disconnected writing
- Neat, average, and difficult handwriting
- Consistent writer style within one patient's multi-page record
- Different writer styles across patients

The exact rendered text must remain correct. If a generative handwriting model changes a
character, discard and regenerate the sample or route it to manual review.

GROUND-TRUTH GENERATION
-----------------------
Generate values with deterministic code and schema-aware rules. Examples:

- parity <= gravidity
- living_children <= parity
- systolic_bp > diastolic_bp
- postpartum dates occur after delivery
- follow-up dates occur after consultation
- cesarean indication is only applicable to cesarean delivery
- units match the field
- boolean and categorical values belong to the allowed set

Include all field statuses:

- KNOWN
- NOT_PROVIDED
- ILLEGIBLE
- NOT_APPLICABLE
- NEEDS_REVIEW

Blank fields must be deliberately labeled NOT_PROVIDED. Do not confuse blank, illegible, and
not applicable.

IMAGE VARIATION AND DISTORTIONS
-------------------------------
Keep a clean version internally, then generate degraded versions. Randomly combine:

- Perspective distortion and keystone effects
- Rotation and skew
- Partial cropping near page edges
- Scale and resolution changes
- Defocus blur
- Motion blur in several directions
- Gaussian and sensor noise
- JPEG compression artifacts
- Uneven illumination
- Directional shadows
- Low light and overexposure
- White-balance and color-temperature changes
- Paper texture and mild wrinkles
- Faint print
- Faint pen and ink bleed
- Background/table visible around the page
- Small finger occlusion away from critical values
- Writing crossing a line or touching a box
- Crossed-out answers and rewritten answers, with explicit annotations
- Empty, double-marked, and ambiguous checkboxes

Use four difficulty levels: clean, mild, medium, and heavy. Keep the distribution balanced
enough to evaluate performance by difficulty. Do not make every sample heavily degraded.

When geometric distortion is applied, transform every field bounding box with the same
homography. Bounding boxes must correspond to the final saved image, not the clean image.

LABEL FORMAT
------------
Each form-specific labels.csv must have one row per full-page image and include at least:

- image_filename
- record_id (random synthetic identifier)
- form_id
- language
- writer_style_id
- difficulty
- random_seed
- distortion_json
- bboxes_json
- transcriptions_json
- one column for every canonical field value in that form

Each annotations.jsonl record must include:

{
  "image_filename": "...",
  "record_id": "...",
  "form_id": "...",
  "language": "fr",
  "writer_style_id": "writer_0042",
  "difficulty": "medium",
  "distortions": {...},
  "fields": {
    "weight_g": {
      "canonical_value": 5218,
      "rendered_text": "5218 g",
      "type": "double",
      "unit": "g",
      "status": "KNOWN",
      "bbox": [x1, y1, x2, y2],
      "crop_filename": "..."
    }
  }
}

Use normalized final-image coordinates from 0 to 1 for bounding boxes.

DATA SPLITS
-----------
Create train, validation, and synthetic-test split files. Split by writer_style_id and
record_id, never randomly by individual page or crop. A writer style or synthetic patient must
exist in only one split.

Suggested split:

- 80% train
- 10% validation
- 10% synthetic test

The organizer dataset remains a completely separate final test set and must not influence
generation or tuning.

QUALITY CONTROL
---------------
Automatically verify:

1. Every image opens successfully.
2. Every CSV row has a corresponding image.
3. Every annotation points to an existing image and crop.
4. Every field bbox is inside the final image.
5. Every rendered transcription matches the intended text.
6. Arabic strings have correct shaping and direction.
7. Values pass schema and cross-field validation.
8. No direct identifiers are present.
9. Counts are balanced by form, language, difficulty, and status.
10. Duplicate and near-duplicate rates are reported.

For generative handwriting, run at least two OCR/VLM readers as quality filters. Reader
agreement is not ground truth; it only identifies samples that need regeneration or review.
Manually inspect a random contact sheet from every form/language/difficulty combination.

CUDA AND PERFORMANCE
--------------------
- Detect CUDA at startup.
- Use batched generation.
- Use PyTorch/Kornia GPU augmentation when practical.
- Use mixed precision where safe.
- Use parallel CPU workers for font rendering and file encoding.
- Stream annotations to disk rather than retaining the whole dataset in memory.
- Support --resume so an interrupted run does not restart completed images.
- Log images/second, GPU name, CUDA version, output size, and error counts.

DELIVERABLES
------------
Implement and run:

1. A configurable generator script.
2. A configuration file defining counts, languages, distributions, and distortion ranges.
3. A smoke test.
4. Automated integrity tests.
5. A contact-sheet preview for each form and language.
6. A final report containing counts, balance, disk size, failures, and CUDA usage.

Do not stop after writing pseudocode. Build the generator, run the smoke test, inspect the
previews, fix obvious problems, and then run the requested full generation on the stronger
computer.
